8. FINANCIAL LEDGER AND ACCOUNTING

Build a double-entry financial ledger before enabling real financial operations.

This is a critical architectural requirement.

Ledger principles

* Every financial movement creates balanced debit and credit entries.
* Each ledger transaction is atomic.
* Posted ledger entries are immutable.
* Corrections use traceable reversing entries rather than editing historical records.
* Monetary amounts use exact decimal arithmetic or integer base units, never JavaScript floating-point calculations.
* Every entry records its asset, account, transaction reference and timestamps.
* Available, reserved and pending amounts are tracked consistently.
* Internal transfers preserve accounting integrity.
* Reconciliation compares internal records against provider and blockchain data.

Implement:

* Ledger accounts.
* Journal transactions.
* Journal entries.
* Customer asset balances.
* Pending and reserved funds.
* Deposit accounting.
* Withdrawal accounting.
* Trade settlement.
* Fees and commissions.
* Reversals and refunds where appropriate.
* Reconciliation reports.
* Suspense accounts for unresolved movements.

Add database constraints and tests that prevent unbalanced transactions, duplicate processing and negative available balances where prohibited.

Use idempotency keys for all money-moving APIs. Protect concurrent operations with appropriate database transactions, row locking or equivalent concurrency controls.

Never let the frontend directly set a user’s balance.

9. SEND AND RECEIVE WORKFLOWS

Implement a complete transaction lifecycle.

1. Customer selects an asset and network.
2. System validates the destination and account eligibility.
3. System retrieves a current fee estimate.
4. System checks balance, limits and available funds.
5. Customer sees the full transaction preview.
6. Customer explicitly confirms.
7. Additional authentication is required when appropriate.
8. The backend reserves funds atomically.
9. Risk and compliance checks are performed.
10. The signing provider authorizes and signs the transaction.
11. The transaction is broadcast.
12. The worker monitors provider events and blockchain confirmations.
13. The ledger is updated through an idempotent workflow.
14. The transaction becomes completed, failed or requires review.
15. The customer receives an accurate status notification.

Use explicit state transitions and prevent invalid transitions.

Handle provider timeouts, webhook retries, duplicate events, chain reorganizations, stuck transactions, insufficient gas and ambiguous broadcast outcomes.

Never release reserved funds merely because a request timed out. Reconcile uncertain outcomes before deciding whether funds should be released.

Receiving crypto must support pending, confirmed and failed states with configurable confirmation requirements.
