CKS CRYPTO KLEIN SHOP — MASTER FULL-STACK BUILD PROMPT

1. Your role and objective

Act as a senior fintech product designer, full-stack engineer, blockchain engineer, database architect, and application security specialist.

Build CKS Crypto Klein Shop, a premium cryptocurrency platform with a trustworthy German fintech identity. The platform must support real-time cryptocurrency prices, user accounts, individual wallets, a native CKS digital currency, internal transfers between registered users, and a secure financial transaction ledger.

Do not build only a landing-page mockup. Inspect the existing repository, preserve working components, identify incomplete features, and implement the complete application in production-oriented phases.

Create a consistent CKS brand mark and a custom CKS coin emblem with a recognizable, original design. Do not copy the Bitcoin logo.

5. CKS digital currency

Create the platform’s own digital currency with the symbol CKS.

Initial product rules

* Reference price: 1 CKS = €1.
* Eligible new registrations receive a one-time bonus of 50 CKS.
* Initial bonus display: “50 CKS bonus — reference value €50.”
* Users can send CKS to other registered CKS users.
* Users can receive CKS from other registered CKS users.
* Users can view their available balance and complete CKS transaction history.
* Every CKS movement must be auditable.

Critical economic distinction

Implement the €1 figure as a clearly labeled platform reference valuation unless and until a legally and financially supported redemption mechanism exists.

Do not claim that CKS is exchange-traded, cash-equivalent, guaranteed to maintain a market price, or redeemable for €1 without the corresponding infrastructure and legal arrangements.

Create explicit configuration and documentation for:

* Reference price.
* Total issued supply.
* Circulating supply, if applicable.
* Bonus issuance.
* Transfer rules.
* Redemption status.
* Fees, if any.
* Whether CKS is an internal ledger asset or an on-chain token.

Do not mix CKS with real EUR bank balances or other cryptocurrency balances.

Choose and document the CKS implementation model

Default MVP: implement CKS as a platform-issued ledger asset, recorded in the database and transferable between authenticated users. This enables working internal transfers without pretending that an external blockchain transaction occurred.

Optional blockchain phase: if an actual on-chain CKS token is required, implement a separately audited smart contract on a selected network. Document the network, contract address, token decimals, supply and minting rules, wallet custody model, and transaction fees. Do not invent a deployed contract address or claim deployment without proof.

If the platform’s 50 CKS bonus is intended to be an actual on-chain token, implement an explicitly authorized and funded issuance process. Never silently create real on-chain tokens through a database update.

6. Registration and 50 CKS bonus

Implement secure registration and a one-time welcome bonus.

Flow:

1. User registers with email and password.
2. Email verification is completed.
3. The backend checks eligibility and account status.
4. The database creates the user and wallet records.
5. The backend grants exactly 50 CKS through an atomic ledger transaction.
6. The user sees the credited amount and a welcome notification.
7. The transaction is recorded in the account’s history.

Security rules:

* One bonus per eligible account.
* Enforce uniqueness and idempotency at the database level.
* Prevent duplicate awards during retries or simultaneous requests.
* Apply appropriate bot, rate-limit, and duplicate-account protections.
* Define eligibility and abuse-review rules.
* Never award bonuses from client-side code.
* Use a configurable feature flag to pause bonus issuance.
* Keep an immutable audit record of every bonus.
* Do not delete ledger history to correct errors; use explicit reversal entries.

Make the bonus terms visible before registration. Explain any transfer, withdrawal, expiration, verification, or redemption restrictions accurately. Do not invent restrictions after users have received the bonus.

7. Internal CKS transfers

Implement functional transfers between registered platform users.

Example:

* User A owns 50 available CKS.
* User A sends 10 CKS to User B.
* User A has 40 CKS available.
* User B receives 10 CKS.
* Both users see the same transaction reference and matching transfer records.

Requirements:

* Recipient lookup using verified platform identities.
* Amount validation and decimal precision.
* Minimum and maximum limits configured server-side.
* Optional transfer notes.
* Confirmation screen showing recipient, amount, and applicable fees.
* PIN or re-authentication for sensitive transactions where appropriate.
* Atomic debit and credit in one database transaction.
* Row locking or equivalent concurrency protection.
* Idempotency keys for transfer requests.
* Unique transaction identifiers.
* Prevention of negative balances and double spending.
* Clear pending and completed states.
* Risk-based limits and suspicious-activity monitoring.
* Reversal entries and administrative review workflows.

Never trust a balance or transaction amount submitted by the browser. All balance calculations and transfer authorization must occur on the server.

For internal transfers, no blockchain network fee should be displayed unless a real fee applies. Do not generate fake blockchain transaction hashes.

8. Real cryptocurrency trading and external wallets

Build the architecture for real trading and blockchain transactions, but do not simulate execution as if it were real.

For each external integration:

* Select and configure a suitable provider.
* Secure credentials in environment variables or a secrets manager.
* Implement server-side validation and error handling.
* Record provider references and execution status.
* Support idempotency, reconciliation, and audit logs.
* Display network fees and confirmation requirements.
* Handle pending, failed, cancelled, and completed states honestly.

Do not label a demo trade as executed on an exchange. Do not label an internal wallet entry as a blockchain deposit.

If exchange, payment, custody, or blockchain providers have not been configured, display an explicit sandbox or unavailable state and provide a clear setup checklist.

Never collect or store users’ raw wallet seed phrases or private keys in the ordinary application database.

* Password reset with short-lived, single-use tokens.
* Login rate limits and brute-force protection.
* Optional multi-factor authentication.
* Secure cookie settings when cookie-based sessions are used.
* Server-side authorization for every protected endpoint.
* Input validation and output encoding.
* CSRF protection where applicable.
* Protection against SQL injection, XSS, IDOR, and replay attacks.
* Security event logs and session revocation.
* Privacy-aware logging that never exposes secrets.

Use least-privilege access for administrators and service credentials.
